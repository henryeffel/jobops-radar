## Session 02 — Evidence ID 기반 LLM 계약

### 목표

LLM이 공고·이력서 근거 문장을 정확히 복사해야 했던 불안정한 계약을 제거하고, 서버가 만든 구조화 JSON의 evidence ID만 참조하게 합니다.

### 변경 사항

- 공고와 Markdown 이력서를 최대 80개의 bounded section으로 나누는 `structured_input` module을 추가했습니다.
- 공고 section에는 `job-001`, 이력서 section에는 `candidate-001` 형태의 안정적인 ID를 부여했습니다.
- 이력서의 summary, skills, projects, education, certifications도 candidate JSON에 포함했습니다.
- LLM 출력에서 `matched`, 근거 원문 문자열을 제거하고 `job_evidence_ids`, `profile_evidence_ids`를 사용합니다.
- 서버는 존재하지 않는 evidence ID를 거부하고 ID가 가리키는 원문을 API 응답의 근거로 복원합니다.
- matched 여부와 적합도는 profile evidence ID와 importance를 이용해 서버에서 계산합니다.
- 단일 JSON code fence, singleton ID 문자열, singular ID field와 `null` 목록을 제한적으로 정규화합니다.
- schema validation 실패에는 개인정보 없는 필드 위치와 오류 유형을 포함하도록 개선했습니다.
- SDK 자동 재시도를 비활성화하고 provider timeout을 50초로 낮춰 전체 요청이 약 1분 안에 fallback할 여유를 확보했습니다.

### 검증

- `python -m pytest -q -p no:cacheprovider`: 당시 69 passed, 후속 규칙 테스트 추가 후 73 passed.
- 구조화 입력의 ID 안정성, 존재하지 않는 ID 거부, 안전한 JSON 변형 정규화를 테스트했습니다.
- 실제 입력은 공고 16개, 이력서 29개 section으로 변환됐습니다.
- 첫 실제 evidence ID 호출은 38.2초 후 Pydantic schema validation에 실패했습니다.
- 정규화 후 재호출은 60초 안에 완료되지 않아 종료했습니다.
- 이후 작은 evidence ID 입력이 20.9초에 성공했습니다. 전체 입력 실패 원인은 `profile_evidence_ids`가 5개를 넘은 두 항목으로 특정했습니다.
- 중복 ID를 제거하고 최대 5개로 제한하는 정규화 후 실제 `resume_sample.md` 전체 분석이 17.1초에 성공했습니다. LLM은 16개 요구사항을 반환했고 서버 계산 점수는 최초 61점이었습니다.
- 성공 결과 검토에서 `requirements` 안의 `required` 부분 문자열과 설명문의 일반적인 `must`가 필수 조건으로 오탐되는 문제를 발견했습니다. 필수·우대 판정은 section heading과 명시적 문구만 사용하도록 보정하고 회귀 테스트를 추가했습니다.
- 최초 61점은 판정 규칙 보정 전 실험값이며 제품 품질이나 후보자 평가 지표로 사용하지 않습니다.
