### Backend Concepts Used

This task introduced bounded offset pagination, FastAPI query validation,
SQLAlchemy limit/offset composition, and deterministic multi-column ordering.
The API rejects invalid pagination inputs at the HTTP boundary before querying
the database.

### CS / DSA Concepts Used

No major DSA was introduced. The closest CS concept is total ordering:
`created_at` alone can tie, while the unique `id` tie-breaker makes the ordered
pair deterministic. Offset pagination slices an ordered sequence but can shift
when concurrent inserts change the prefix.

### Design Decisions

The endpoint uses simple limit/offset pagination because total counts, cursors,
filtering, and search are explicitly outside v1. The maximum limit is 100 to
bound response and application work. Validation remains in FastAPI while query
construction remains in the service.

No new ADR was required because this is an incremental API capability within
the existing FastAPI and SQLAlchemy architecture.

### Issues / Warnings

- Offset pagination can produce shifted pages when data changes between
  requests and can become inefficient at large offsets.
- No total count, cursor, filter, or search metadata is returned.
- PostgreSQL behavior remains unverified locally while Docker is unavailable.
- The existing Starlette `TestClient` deprecation warning remains non-blocking.

### Next Task

Add a GitHub Actions workflow that runs tests and source compilation on pull
requests using SQLite. Add PostgreSQL CI separately when its integration scope
is ready.

### Backend Concepts Used

This task introduced a one-to-many relational model, non-null foreign-key
linkage, a foreign-key lookup index, layered Pydantic/database validation, and a
small framework-independent persistence service for a child entity.

### CS / DSA Concepts Used

No major DSA was introduced. The closest concepts are referential integrity and
indexed parent-child lookup. Requirements are returned in deterministic `id ASC`
order so manually curated input order is stable for an unchanged dataset.

### Design Decisions

Requirement categories remain strings instead of a database enum so the early
taxonomy can evolve without enum-specific migration overhead. Pydantic restricts
the current accepted values. Importance is enforced at both schema and database
layers because it is a stable domain invariant.

Deletion cascade behavior was deliberately left unspecified because no delete
workflow exists yet. The service checks parent existence in addition to the
foreign key, providing a clear domain error and consistent SQLite tests.

No ADR was created because this is an incremental domain-storage capability
inside the accepted SQLAlchemy/Alembic architecture, not a new architectural
direction.

### Issues / Warnings

- JobRequirement has no HTTP API yet.
- The six Carrot requirements are test data, not production seed data.
- SQLite can differ from PostgreSQL in foreign-key and constraint behavior;
  PostgreSQL runtime validation remains pending.
- Requirement taxonomy changes must update schema validation and tests.

### Next Task

Add small nested create/list JobRequirement API operations and route tests,
without adding analysis summaries, LLM extraction, candidate profiles, or
Auth/OIDC.
