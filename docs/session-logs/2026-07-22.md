## Session 01 — Liveness와 readiness health check 분리

### 목표

FastAPI process 자체의 생존 여부와 DB-backed 기능의 준비 상태를 서로 다른 endpoint로 관찰할 수 있게 합니다. DB 장애가 발생해도 process가 살아 있다는 신호는 유지하고, 운영 응답과 로그에 내부 연결 정보를 노출하지 않습니다. 현재 자동화 검증은 SQLite와 교체한 실패 dependency를 사용하며 실제 PostgreSQL 검증은 후속 작업입니다.

### 변경 사항

- health endpoint를 `app/api/routes_health.py`의 전용 router로 분리했습니다.
- `GET /health/live`는 외부 dependency를 확인하지 않고 `200`과 `{"status":"alive"}`를 반환합니다.
- `GET /health/ready`는 현재 DB session에서 `SELECT 1`을 실행합니다.
- DB query가 성공하면 `200`과 `{"status":"ready"}`를 반환합니다.
- SQLAlchemy DB 오류가 발생하면 `503`과 `{"status":"not_ready"}`를 반환합니다.
- readiness 실패 로그에는 예외 원문이나 DB URL을 기록하지 않고 고정된 warning만 남깁니다.
- 기존 `GET /health`는 기존 client와 점검 절차의 호환성을 위해 유지했습니다.
- OpenAPI summary와 description에서 liveness와 readiness의 의미를 구분했습니다.

### 테스트

- 기존 `/health` 호환 응답을 검증했습니다.
- DB 정상 상태의 liveness `200`과 readiness `200`을 검증했습니다.
- dependency override로 DB query 실패를 재현했습니다.
- DB 장애 중 readiness는 `503`, liveness는 `200`을 유지하는지 검증했습니다.
- 가상의 DB URL, 사용자명과 비밀번호가 HTTP 응답과 warning log에 포함되지 않는지 검증했습니다.

- 남은 warning은 FastAPI/Starlette `TestClient`의 upstream deprecation 1건입니다.

### 설계 결정

- liveness는 process 응답 가능성만 나타내며 DB나 외부 LLM 상태에 의존하지 않습니다.
- readiness는 현재 DB-backed 요청을 처리할 수 있는지를 나타냅니다.
- readiness는 가벼운 `SELECT 1`만 실행하며 migration 완료 여부나 전체 사용자 여정을 검사하지 않습니다.

## Session 02 — Request ID와 구조화 HTTP 완료 로그

### 목표

HTTP 요청과 운영 로그를 하나의 request ID로 연결하고, `journalctl`에서도 검색 가능한 최소 JSON 로그를 남깁니다. 사용자 입력과 credential은 완료 로그 범위에서 제외합니다.

### 계약

- header 이름은 `X-Request-ID`입니다.
- 외부 값은 ASCII 영문 대·소문자, 숫자, `.`, `_`, `-`로 구성된 1~128자만 재사용합니다.
- 값이 없거나 안전하지 않으면 UUID4로 교체하며 요청 자체를 실패시키지 않습니다.
- 응답 header와 완료 로그는 동일한 request ID를 사용합니다.
- CORS에서 `X-Request-ID`를 expose합니다.
- 완료 로그는 event, request ID, method, path, status code와 elapsed milliseconds만 포함합니다.

### 변경 사항

- `app/core/request_tracing.py`에 request tracing middleware를 추가했습니다.
- 각 요청의 request ID를 `request.state`와 `ContextVar`에 저장하여 하위 서비스에서 참조할 수 있게 했습니다.
- 완료 로그를 한 줄 JSON의 `http_request_completed` event로 기록합니다.
- URL query string, header와 request body를 완료 로그에 포함하지 않습니다.
- LLM fallback 로그를 `llm_fallback` event, 동일한 request ID와 안정적인 reason code로 기록합니다.
- 외부 provider exception 원문은 fallback 로그에서 제거했습니다.
- 처리되지 않은 500 예외도 generic 응답과 `X-Request-ID`를 반환합니다.
- 500 오류 로그에는 exception type과 stack frame을 남기되 exception 원문은 redaction합니다.

### 테스트

- 안전한 외부 request ID의 재사용과 응답·로그 일치를 검증했습니다.
- request ID 누락 시 UUID 생성을 검증했습니다.
- 허용하지 않은 문자와 128자 초과 값의 UUID 교체를 검증했습니다.
- 128자 경계값은 그대로 허용되는지 검증했습니다.
- query string과 Authorization header의 가상 secret이 로그에 포함되지 않는지 검증했습니다.
- frontend origin 응답에서 `X-Request-ID`가 CORS에 expose되는지 검증했습니다.
- 처리되지 않은 500 응답과 실패·완료 로그가 동일한 request ID를 사용하는지 검증했습니다.
- 500 오류의 가상 secret 원문이 응답과 로그에 포함되지 않는지 검증했습니다.

## Session 03 — 공고 목록 filter, sort와 pagination

### 목표

실제 공고 조회 패턴을 API와 service에 명시하고, 이후 PostgreSQL 실행 계획과 index 검증에 사용할 query를 확정합니다.

### 조회 계약

- `company_name`은 회사명 정확 일치 filter입니다.
- `is_active`는 `true`와 `false`를 모두 명시적으로 filter합니다.
- `sort=created_at`은 기존 기본값인 `created_at DESC, id DESC`를 유지합니다.
- `sort=expiration_date`는 마감일 오름차순, `NULLS LAST`, `id DESC` tie-break를 사용합니다.
- filter와 sort를 적용한 결과에 `limit` 1~100과 0 이상의 `offset`을 적용합니다.
- 알 수 없는 sort 값과 잘못된 pagination 값은 FastAPI validation으로 422를 반환합니다.

### 변경 사항

- `JobPostingSort` enum으로 허용하는 정렬 값을 OpenAPI 계약에 반영했습니다.
- `list_job_postings` service가 선택적인 회사명·활성 상태 조건과 정렬 방식을 조합합니다.
- route가 query parameter를 검증해 service에 전달합니다.
- 마감일이 같은 경우에도 pagination 순서가 흔들리지 않도록 ID tie-break를 유지합니다.
- 아직 index를 추가하지 않았습니다. 실제 PostgreSQL 데이터와 `EXPLAIN ANALYZE` 측정 전에는 index 효과를 가정하지 않습니다.

## Session 04 — 공고와 요구사항 묶음 transaction rollback

### 목표

공고와 여러 요구사항을 하나의 원자적 작업으로 저장하고, 중간 단계에서 실패하면 일부 데이터가 남지 않도록 보장합니다. rollback 이후에도 같은 SQLAlchemy session을 정상적으로 다시 사용할 수 있어야 합니다.

### 변경 사항

- 아직 공고 ID가 없는 요구사항 입력을 `JobRequirementDraft`로 분리했습니다.
- `create_job_posting_with_requirements` service를 추가했습니다.
- service는 공고를 flush해 ID를 확보하고 요구사항을 같은 transaction에 추가한 뒤 마지막에 한 번만 commit합니다.
- `IntegrityError` 발생 시 rollback하고 내부 DB 예외 대신 `JobPostingBundleConstraintError`를 반환합니다.
- 예상치 못한 다른 예외도 rollback한 뒤 원래 예외를 다시 전달합니다.
- 기존 단건 공고·요구사항 생성 service와 API 계약은 변경하지 않았습니다.
- bundle 저장은 현재 service 경계이며 별도 HTTP route는 추가하지 않았습니다.

### 테스트

- 공고 1개와 요구사항 2개의 정상 commit을 검증했습니다.
- 두 번째 요구사항의 DB check constraint 실패 시 공고와 모든 요구사항이 남지 않는지 검증했습니다.
- 두 번째 flush에서 예상치 못한 오류를 발생시켜 전체 rollback되는지 검증했습니다.
- rollback 직후 같은 session으로 정상 bundle을 다시 저장할 수 있는지 검증했습니다.
- 중복 공고 unique constraint 오류가 안정적인 service 오류로 변환되고 기존 데이터만 유지되는지 검증했습니다.

Pydantic validation을 우회한 invalid fixture는 정상 API 입력을 모방하기 위한 것이 아니라 DB constraint가 transaction의 최종 방어선으로 동작하는지 시험하기 위한 용도입니다.

### 검증 결과

- transaction 전용 테스트: 5 passed.
- `python -m pytest -q -p no:cacheprovider`: 101 passed.
- 남은 warning은 FastAPI/Starlette `TestClient`의 upstream deprecation 1건입니다.

### 한계와 다음 작업

현재 자동화 검증은 SQLite에서 수행했습니다. PostgreSQL의 실제 transaction, constraint와 동시성 동작은 PostgreSQL 통합 환경에서 다시 검증해야 합니다. 다음으로 PostgreSQL 테스트 데이터를 준비하고 Ticket 4의 `EXPLAIN ANALYZE`와 index 적용 전 측정을 수행합니다.

## Session 06 — PostgreSQL 실행 환경 선택과 EC2 접속 진단

### 목표

실제 PostgreSQL query plan을 측정할 실행 환경을 정하고, 설치나 서버 변경 전에 사용 가능한 로컬·원격 환경을 확인합니다.

### Docker·WSL 확인

- 로컬 Windows는 Windows 10 Pro 22H2, build 19045, 64-bit입니다.
- Docker와 PostgreSQL 관련 로컬 command는 설치되어 있지 않습니다.
- WSL은 최신 version 정보를 출력하지 못하고 설치 안내만 제공했으며 Linux distribution도 확인되지 않았습니다.
- `winget`은 현재 환경에서 실행되지 않았습니다.
- WSL 기반을 준비하기 위해 `wsl --install --no-distribution`을 시도했지만 사용자 중단으로 완료 여부를 확인하지 못했습니다.
- 따라서 WSL 또는 Docker Desktop이 설치·활성화됐다고 기록하지 않습니다. 재개 전에 `wsl --status`를 다시 확인해야 합니다.

### 환경 결정

Windows에 PostgreSQL을 직접 설치하는 대신 기존 Ubuntu EC2에서 PostgreSQL을 검증하는 경로를 우선 선택했습니다. 이 경로는 PostgreSQL query·transaction 검증과 Linux service·로그·장애 대응 경험을 같은 환경에서 연결할 수 있습니다.

보안 원칙은 다음과 같습니다.

- SSH private key의 내용과 DB credential을 문서·로그에 기록하지 않습니다.
- PostgreSQL 5432를 `0.0.0.0/0`에 공개하지 않습니다.
- 가능하면 application과 benchmark를 EC2 내부에서 실행합니다.
- 원격 DB 접근이 필요하면 제한된 Security Group 또는 SSH tunnel을 사용합니다.

### EC2 접속 진단

- 사용자가 제공한 기존 EC2 public IP와 Ubuntu 사용자를 기준으로 접속을 시도했습니다.
- 로컬 Downloads의 지정된 PEM 파일이 존재하는 것은 확인했으며 key 내용은 읽거나 출력하지 않았습니다.
- SSH는 인증 단계 전에 port 22 connection timeout으로 종료됐습니다.
- 같은 public IP의 80, 443과 8000 port도 제한 시간 내 연결되지 않았습니다.
- 이 결과만으로 인스턴스 중지, public IP 변경 또는 Security Group 차단 중 어느 원인인지 확정할 수 없습니다.
- 인증 단계에 도달하지 않았으므로 SSH key 또는 사용자명이 틀렸다고 판단할 근거도 없습니다.

### 현재 blocker

AWS 콘솔에서 다음을 확인해야 합니다.

1. 인스턴스가 `Running` 상태인지 확인합니다.
2. 현재 public IPv4 또는 public DNS를 확인합니다.
3. SSH TCP 22 inbound source가 작업자의 현재 public IP를 허용하는지 확인합니다.
4. 인스턴스를 중지·시작해 IP가 변경됐다면 새 주소를 사용합니다.

### 다음 작업

SSH 접속이 복구되면 먼저 OS, CPU·memory·disk, 실행 중인 service, open port와 PostgreSQL 설치 여부를 읽기 전용으로 점검합니다. 그 결과를 확인한 뒤에만 PostgreSQL 설치와 migration을 진행합니다.
