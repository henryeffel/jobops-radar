# 지원 의사결정부터 지원 관리까지의 제품 로드맵

기준일: 2026-07-21

## 결정 사항

1차 통합 MVP 회고 이후 논의한 아이디어 #1부터 #4까지를 JobOps의 공식적인 다음 제품 방향으로 채택합니다.

1. 지원 판단 엔진
2. Apply Now 지원 자료 생성
3. 지원 공고와 진행 상태 관리
4. 여러 공고 비교와 지원 우선순위 추천

네 기능은 독립된 부가 기능이 아니라 하나의 사용자 흐름입니다.

```text
공고 저장
→ 지원 판단
→ Apply Now 지원 자료 생성
→ 지원 상태 관리
→ 여러 공고 우선순위 비교
```

각 단계가 해결하는 사용자 질문은 다음과 같습니다.

| 단계 | 사용자 질문 | JobOps가 제공할 답 |
| --- | --- | --- |
| 지원 판단 | 이 공고에 지원해도 될까? | 추천, 결격 조건, 강점, 위험 |
| Apply Now | 지원 전에 무엇을 고쳐야 할까? | 이력서 수정안과 지원 자료 |
| 지원 관리 | 지금 어디까지 준비했지? | 공고별 상태와 다음 할 일 |
| 공고 비교 | 어디부터 지원해야 하지? | 설명 가능한 우선순위 |

## 제품 원칙

### 점수가 아닌 결정을 중심에 둔다

기존 점수는 참고 정보로 유지할 수 있지만 합격 확률이나 절대 평가처럼 사용하지 않습니다. 사용자에게 가장 먼저 보여줄 결과는 다음 네 가지 추천 중 하나입니다.

- `apply_now`: 지금 지원
- `apply_after_revision`: 이력서 일부 수정 후 지원
- `apply_after_preparation`: 단기 보완 후 지원
- `deprioritize`: 현재는 지원 우선순위가 낮음

### 부족한 항목의 성격을 구분한다

모든 부족 항목을 학습 과제로 취급하지 않습니다.

- `blocking_gap`: 지원 자격을 실질적으로 막는 조건
- `skill_gap`: 실제 경험이나 역량 보완이 필요한 항목
- `presentation_gap`: 경험은 있으나 이력서 표현이 부족한 항목
- `evidence_gap`: 현재 정보만으로 경험 여부를 판단할 수 없는 항목

이 구분을 통해 사용자가 불필요한 학습 때문에 지원을 미루는 문제를 줄입니다.

### 생성 결과는 제안이며 사용자가 확정한다

Apply Now가 기존 이력서를 자동으로 덮어쓰지 않습니다. 모든 수정안에는 다음 정보가 함께 표시되어야 합니다.

```text
기존 문장
→ 추천 문장
→ 변경 이유
→ 사용한 근거
→ 적용·복사 여부
```

### 공고와 분석 시점의 결과를 분리한다

동일한 공고도 이력서 수정, 프로젝트 추가 또는 분석 정책 변경 이후 다른 결과가 나올 수 있습니다. 따라서 공고와 분석 snapshot을 분리합니다.

```text
JobOpportunity
├─ 회사, 직무, URL, 마감일
├─ 사용자의 지원 상태
└─ AnalysisRun[]
   ├─ 당시 프로필 snapshot
   ├─ 당시 공고 snapshot
   ├─ 지원 판단과 gap
   ├─ 로드맵
   └─ 생성한 지원 자료
```

## 단계 A: 지원 판단 엔진

### 목표

기존 분석 결과를 사용자가 행동을 결정할 수 있는 지원 추천으로 확장합니다.

### 목표 응답

```json
{
  "application_decision": {
    "recommendation": "apply_after_revision",
    "confidence": "medium",
    "summary": "핵심 필수 조건은 대부분 충족합니다.",
    "reasons": [],
    "blocking_gaps": [],
    "risks": [],
    "strengths_to_emphasize": []
  },
  "gaps": [
    {
      "type": "presentation_gap",
      "requirement": "장애 대응 경험",
      "explanation": "프로젝트에는 근거가 있지만 이력서에 충분히 드러나지 않습니다.",
      "evidence_ids": []
    }
  ]
}
```

### 서버 검증 규칙

- LLM과 deterministic fallback이 동일한 schema를 반환합니다.
- 존재하지 않는 공고·프로필 evidence ID는 거부합니다.
- `apply_now` 추천과 `blocking_gap`이 동시에 존재할 수 없습니다.
- 명시적인 필수 조건 미충족이 있으면 추천 이유에서 이를 숨길 수 없습니다.
- confidence는 합격 확률로 표시하지 않습니다.
- 추천 결과는 분석 시점의 입력 snapshot과 함께 저장합니다.

### UI

점수보다 먼저 결정 카드를 보여줍니다.

```text
추천: 이력서 수정 후 지원

지원해야 하는 이유
- 필수 조건 6개 중 5개에 근거가 있음
- 핵심 업무인 API 설계 경험이 확인됨

지원 전 수정할 것
- 장애 대응 경험을 이력서에 명시

지원하지 못하게 하는 조건
- 없음
```

### 완료 조건

- 네 가지 추천 결과가 API schema와 DB에 반영됩니다.
- 네 가지 gap 분류가 근거와 함께 반환됩니다.
- LLM 성공과 fallback 경로가 동일한 계약을 지킵니다.
- 모순되는 추천과 gap을 서버가 차단하거나 보정합니다.
- frontend에서 결정 카드와 gap별 행동을 확인할 수 있습니다.
- 관련 단위·통합·회귀 테스트가 통과합니다.

## 단계 B: Apply Now

### 목표

분석에서 끝나지 않고 실제 지원에 사용할 수 있는 자료를 생성합니다.

### API 방향

분석 API와 산출물 생성 API를 분리합니다.

```text
POST /job-analyses/{analysis_id}/application-assets
```

사용자가 원할 때만 추가 LLM 호출을 수행하여 지연과 provider 사용량을 줄입니다.

### 초기 산출물

- 영향력이 큰 이력서 문장 수정안 3~5개
- 프로젝트 bullet 개선안
- 지원 동기 초안
- 예상 면접 질문과 답변 포인트
- 지원 전 체크리스트

### 검증 원칙

- 모든 구체적인 경력 주장에 profile 또는 추후 GitHub evidence를 연결합니다.
- 근거가 없는 회사명, 수치, 성과와 기술을 생성하지 않습니다.
- 원문과 수정안을 함께 보존합니다.
- 사용자가 적용한 수정안과 거부한 수정안을 구분합니다.
- 외부 LLM 전송 동의를 별도로 확인합니다.

### 완료 조건

- 분석 결과 ID를 기준으로 산출물을 생성할 수 있습니다.
- 재호출 없이 기존 산출물을 다시 조회할 수 있습니다.
- 사용자가 수정안을 복사하거나 선택적으로 적용할 수 있습니다.
- 근거가 없는 생성 결과를 검증 단계에서 차단합니다.
- provider 실패가 기존 분석 결과 조회를 방해하지 않습니다.

## 단계 C: 지원 보드

### 목표

한 번의 분석 도구에서 반복적으로 사용하는 지원 워크스페이스로 발전시킵니다.

### 주요 모델

- `JobOpportunity`
- `ApplicationStatus`
- `AnalysisRun`
- `ApplicationAsset`

### 초기 지원 상태

- `saved`
- `analyzed`
- `preparing`
- `ready`
- `applied`
- `document_passed`
- `interview`
- `rejected`
- `offered`
- `withdrawn`

초기 UI는 복잡한 Kanban 대신 회사, 직무, 추천, 마감일, 현재 상태와 다음 할 일을 보여주는 목록으로 시작합니다.

### 완료 조건

- 사용자가 분석한 공고를 저장하고 다시 볼 수 있습니다.
- 공고별 지원 상태를 변경할 수 있습니다.
- 한 공고에 여러 분석 snapshot을 저장할 수 있습니다.
- 최신 분석과 이전 분석의 핵심 변화가 구분됩니다.
- 공고 삭제와 사용자 데이터 보존 정책이 명확합니다.

## 단계 D: 공고 비교와 우선순위

### 목표

여러 공고 중 어디에 먼저 시간과 노력을 투입할지 설명 가능한 순서를 제공합니다.

### 기본 기준

- 필수 조건 충족 정도
- blocking gap 존재 여부
- 준비에 필요한 예상 시간
- 공고 마감일
- 사용자의 선호 직무와 조건
- 보유 근거의 품질
- 직무와 프로젝트의 연관성

서버가 설명 가능한 기본 우선순위 값을 계산하고 LLM은 비교 설명을 생성합니다. 최종 순위를 LLM의 불투명한 단일 판단에만 맡기지 않습니다.

```text
우선순위 =
  필수 조건 충족
  + 사용자 선호
  + 마감 임박도
  + 근거 품질
  - 준비 시간
  - blocking gap 위험
```

이 공식은 제품 정책을 설명하는 개념식이며, 실제 가중치는 사용자 피드백과 검증 결과 없이 합격 가능성 수치로 해석하지 않습니다.

### UI 예시

| 공고 | 지원 준비도 | 예상 준비 시간 | 마감 | 추천 |
| --- | ---: | ---: | --- | --- |
| A사 Backend | 높음 | 30분 | 3일 후 | 오늘 지원 |
| B사 Platform | 중간 | 3시간 | 7일 후 | 내일 준비 |
| C사 DevOps | 낮음 | 2주 | 5일 후 | 보류 |

### 완료 조건

- 저장한 공고 두 개 이상을 같은 기준으로 비교할 수 있습니다.
- 추천 순서의 주요 원인을 사용자에게 설명합니다.
- 마감일과 예상 준비 시간이 우선순위에 반영됩니다.
- 사용자가 추천 순서를 직접 조정할 수 있습니다.
- 우선순위를 합격 확률로 오인하지 않도록 안내합니다.

## 구현 순서

아이디어 #1부터 #4까지를 모두 제품 로드맵으로 채택하지만 한 번의 큰 변경으로 구현하지 않습니다.

```text
Decision
→ Assets
→ Tracking
→ Comparison
```

구체적인 순서는 다음과 같습니다.

1. `ApplicationDecision`, `GapClassification`, `EvidenceReference` 설계
2. 지원 판단·gap API와 서버 검증
3. 결정 카드 UI
4. `RoadmapTask`, `ResumeRewrite`, `ApplicationAsset` 설계
5. Apply Now API와 검토 UI
6. `JobOpportunity`, `AnalysisRun`, 지원 상태 모델
7. 지원 공고 목록과 상태 관리 UI
8. 서버 기반 우선순위 계산
9. 공고 비교 UI와 LLM 비교 설명

이번 다음 구현 단위는 **지원 판단 + gap 분류 + 결정 카드 UI**로 제한합니다. 이후 기능들이 이 데이터 계약과 분석 snapshot을 공통 기반으로 사용하기 때문입니다.

## 구현 전에 확정할 정책

각 단계에 착수하면서 다음 정책을 명시적으로 결정합니다.

1. 네 가지 추천 등급의 정확한 판정 기준
2. 네 가지 gap의 분류 기준과 우선순위
3. 지원 상태 간 허용되는 전환
4. 공고 원문, 프로필 snapshot과 산출물의 보존 기간
5. 첫 Apply Now 산출물의 범위
6. 분석·산출물 생성별 외부 LLM 동의 처리
7. 공고 우선순위의 기본 계산 기준과 사용자 조정 방식

## 현재 제외하는 범위

- 채용 사이트 양식을 자동으로 작성하거나 제출하는 기능
- 합격 확률 예측
- 모든 GitHub 소스 파일의 자동 분석
- private GitHub repository OAuth
- 모든 채용 사이트 crawler
- PDF 디자인 편집기
- 자체 모델 fine-tuning
- LLM provider 간 자동 비교

GitHub 근거 수집은 단계 B의 산출물 품질이 실제로 유용하다는 것을 확인한 뒤 별도 단계로 추가합니다.
