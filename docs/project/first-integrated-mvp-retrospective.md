# 1차 통합 MVP 후기 및 개선 방향

기준일: 2026-07-21

## 1. 처음 만들고 싶었던 서비스

JobOps의 출발점은 취업준비생이 반복해서 겪는 다음 두 가지 질문이었습니다.

1. 이 채용공고에 내가 지원해도 되는가?
2. 지원한다면 무엇을 어떤 순서로 준비해야 하는가?

더 나아가 사용자의 이력서와 입력된 채용공고 URL을 바탕으로 외부 LLM이 실제 지원 과정에 바로 활용할 수 있는 산출물을 만들어 주는 서비스를 목표로 했습니다. GitHub 연동을 고려한 이유도 사용자의 기술과 프로젝트 경험을 이력서 문장보다 더 구체적인 근거로 확인하고, 이를 지원 자료 생성에 활용하기 위해서였습니다.

## 2. 1차 통합 MVP에서 구현한 것

현재 시스템은 다음 흐름을 end-to-end로 처리합니다.

```text
회원가입·로그인
→ Markdown 이력서 저장 및 구조화
→ 채용공고 URL 또는 본문 입력
→ HTML·텍스트 추출 및 구조화
→ LLM 또는 deterministic fallback 분석
→ 점수·일치·부족 항목·근거·기초 준비 계획 표시
→ 사용자 프로필 삭제
```

기술적으로 구현한 기반은 다음과 같습니다.

- FastAPI 기반 인증·프로필·분석 API
- React·TypeScript 기반 사용자 UI
- JWT 인증과 사용자별 데이터 격리
- 사용자 입력 URL의 SSRF 기본 방어
- 이력서와 공고의 section·evidence ID 구조화
- Pydantic 기반 LLM structured output 검증
- 서버 측 근거 검증과 점수 계산
- timeout, 동시성 제한, 오류 분류와 deterministic fallback
- 외부 LLM 전송에 대한 명시적 사용자 동의
- 프로필 조회·수정·삭제
- 자동화된 backend 회귀 테스트

## 3. 사용해 보고 느낀 한계

현재 결과는 원래 의도한 취업 실행 도구보다 다음에 더 가깝습니다.

> 사용자의 이력서와 채용공고를 추출하고 비교하여 구조화된 결과를 보여주는 분석기

HTML parser와 text parser는 필요한 입력 기반이지만 그 자체로 사용자가 JobOps를 꼭 사용해야 할 이유가 되지는 않습니다. 현재도 LLM이 비교 분석에 참여하지만, 사용자에게 돌아오는 산출물의 깊이가 부족합니다.

특히 다음 가치가 아직 충분히 구현되지 않았습니다.

- 지원할지 말지에 대한 명확한 추천
- 지원을 막는 필수 결격 조건과 감수 가능한 부족 항목의 구분
- 시간, 우선순위와 완료 기준이 있는 준비 로드맵
- 공고에 맞게 다시 작성된 이력서 문장
- 지원 동기, 자기소개와 cover letter 초안
- 예상 면접 질문과 답변 준비 가이드
- 지원 전 최종 체크리스트
- 생성된 산출물의 저장·수정·재생성

따라서 현재 단계는 최종 제품 MVP라기보다, 그 제품을 만들기 위한 **기반 MVP**로 보는 것이 정확합니다.

## 4. 제품 방향의 재정의

앞으로 JobOps가 제공해야 할 흐름은 다음과 같습니다.

```text
이력서 + 채용공고 + 선택적 GitHub 근거
→ 지원 가능성 판단
→ 강점·위험·결격 조건 설명
→ 개인별 준비 로드맵 생성
→ 지원용 산출물 생성
→ 사용자가 검토·수정·확정
→ 실제 지원
```

제품을 한 문장으로 정의하면 다음과 같습니다.

> JobOps는 채용공고와 후보자의 실제 경험 근거를 비교해 지원 여부를 판단하고, 지원에 필요한 맞춤형 산출물과 실행 로드맵을 생성하는 AI 취업 전략 도구다.

## 5. 다음 MVP의 핵심 출력

### 5.1 지원 판단

단순 점수가 아니라 다음 중 하나의 명시적인 추천을 제공합니다.

- 지금 바로 지원
- 이력서 일부 수정 후 지원
- 단기 보완 후 지원
- 현재는 지원 우선순위가 낮음

판단에는 반드시 다음 근거가 따라야 합니다.

- 추천 이유
- 충족한 핵심 요건
- 지원을 막을 수 있는 결격 조건
- 감수 가능한 부족 항목
- 지원 시 강조할 강점
- 판단 신뢰도와 불확실성

### 5.2 실행 가능한 준비 로드맵

기초 action plan을 다음 속성을 가진 구체적인 작업 목록으로 확장합니다.

- 우선순위
- 권장 완료 시점
- 예상 소요 시간
- 수행할 작업
- 작업이 필요한 이유
- 완료 기준
- 관련된 공고·이력서 근거

예시는 다음과 같습니다.

```text
오늘, 30분
이력서 프로젝트 설명에서 JWT와 장애 대응 경험을 공고 표현에 맞게 수정한다.
완료 기준: 핵심 역량 3개가 구체적인 구현 근거와 함께 표현된다.

지원 전 3일, 2시간
AWS 운영 경험 부족을 보완하기 위해 소규모 EC2 배포를 완료한다.
완료 기준: 공개 URL, 배포 문서와 장애 복구 절차가 존재한다.
```

### 5.3 바로 사용할 수 있는 지원 산출물

- 공고 맞춤형 이력서 bullet 재작성
- 프로젝트 설명 개선안
- 지원 동기 초안
- 자기소개 또는 cover letter 초안
- recruiter에게 보낼 짧은 소개
- 예상 면접 질문과 답변 포인트
- 부족한 경험을 위한 미니 프로젝트 제안
- 지원 전 체크리스트

모든 생성 문장은 사용자의 실제 근거와 연결되어야 하며, 근거가 없는 경험을 새로 만들어서는 안 됩니다.

## 6. 목표 API 구조

다음 단계에서는 분석 응답을 대략 아래와 같은 구조로 확장합니다.

```json
{
  "application_decision": {
    "recommendation": "apply_after_revision",
    "confidence": 0.82,
    "reasons": [],
    "blocking_requirements": [],
    "risks": [],
    "strengths_to_emphasize": []
  },
  "roadmap": [
    {
      "priority": 1,
      "deadline": "today",
      "estimated_minutes": 30,
      "task": "이력서 프로젝트 문장 수정",
      "completion_criteria": "공고 핵심 역량 3개가 근거와 함께 표현됨",
      "evidence_ids": []
    }
  ],
  "application_assets": {
    "resume_rewrites": [],
    "cover_letter_draft": "",
    "motivation_statement": "",
    "interview_questions": [],
    "submission_checklist": []
  }
}
```

LLM은 판단과 문장 생성을 담당하지만, evidence ID 존재 여부, 출력 schema, 금지된 과장 표현과 점수 같은 신뢰 경계는 계속 서버가 검증합니다.

## 7. GitHub 연동의 목적과 범위

GitHub 연동의 목적은 저장소 전체를 무조건 LLM에 전달하는 것이 아닙니다. 이력서에 적힌 기술과 기여 내용을 실제 프로젝트 근거로 보강하고, 이력서에서 누락된 강점을 찾는 것입니다.

우선 활용할 정보는 다음으로 제한합니다.

- README
- dependency·manifest 파일
- 주요 디렉터리 구조
- 테스트 파일과 테스트 개수
- Dockerfile과 CI 설정
- 사용자가 선택한 핵심 소스 파일
- 최근 commit의 제목과 변경 범위 요약

이를 통해 다음 산출물을 개선할 수 있습니다.

- 실제 사용 기술 탐지
- 프로젝트별 기여 내용과 난이도 추정
- 테스트·문서·배포 경험 확인
- 이력서에 빠진 경험 발견
- 과장된 이력서 문장 방지
- 구체적인 공고 맞춤형 bullet 생성

초기 연동은 공개 repository URL과 사용자의 명시적 선택을 기준으로 시작하고, private repository OAuth는 보안·권한 모델을 별도로 설계한 뒤 진행합니다.

## 8. 개선 작업 우선순위

1. `application_decision` 모델과 지원 추천 근거 구현
2. 시간·우선순위·완료 기준을 포함한 roadmap 구현
3. 공고 맞춤형 이력서 문장 생성
4. 지원 동기·cover letter·면접 질문 생성
5. 산출물 검토·복사·수정 UI
6. 산출물 저장과 선택적 재생성
7. 공개 GitHub repository 근거 수집
8. GitHub 근거를 포함한 지원 산출물 생성
9. PDF·DOCX 이력서 입력
10. 사용자 피드백과 실제 지원 결과를 통한 평가 품질 개선

## 9. 기술적 원칙

제품 출력이 확장되어도 다음 원칙은 유지합니다.

- LLM 답변을 그대로 신뢰하지 않는다.
- 모든 중요한 판단과 생성 문장을 사용자 근거에 연결한다.
- 근거가 없는 경력과 성과를 만들어내지 않는다.
- 외부 provider 실패를 서비스 전체 실패로 만들지 않는다.
- 이력서와 repository의 외부 전송은 사용자가 통제한다.
- 자동 생성된 산출물은 사용자가 검토하고 확정한다.
- 점수는 절대적인 합격 확률로 표현하지 않는다.

## 10. 1차 MVP의 의의

1차 MVP가 원래 제품 의도를 모두 달성한 것은 아니지만 헛된 구현은 아닙니다. 인증, 프로필, 안전한 URL 입력, 구조화된 근거, LLM 검증, fallback과 frontend 흐름은 다음 단계의 실행형 기능이 의존할 기반입니다.

이번 회고의 결론은 parser를 더 많이 만드는 것이 아닙니다. 다음 개발의 중심을 다음과 같이 옮기는 것입니다.

> 입력을 잘 읽는 시스템에서, 지원 결정을 돕고 실제 지원 자료를 완성하는 시스템으로 발전시킨다.
